# Private account round history — release-gated pilot
- A verified account and a valid room-seat bearer are separate credentials. Explicit per-round opt-in in setup associates only that seat with that account. No nickname matching, retrospective claiming, client-supplied account ID, or competitive score. Opt out before the round finishes while still signed in to that account; sign-out alone does not revoke prior consent. Account deletion cascades both pending consent and saved personal history. Other participants never receive account IDs or consent status.
- Consent writes lock the room row, require the current revision, enforce setup/play eligibility in SQL, and increment revision atomically. The terminal move CAS, anonymous receipt and personal association are one transaction. Duplicate seat/account conflicts do not transfer ownership. New rooms get an internal UUID; pre-existing rooms without one cannot opt in until they have an archived round. Withdrawal awards no unfinished round. Previous consent does not carry into rematches; each round requires a new opt-in.
- Personal history shows only the latest 50 own nonexpired completed casual rounds. Human and bot counts are explicit. No rank, XP or leaderboard; incomplete opt-in history is not a career record. The API does not expose room codes, UUIDs, names of other players, raw events, private cards, or other placements.
- Apply db/player-accounts-v1.sql, db/room-round-receipts.sql and db/room-private-history.sql to an isolated database. Account and room URLs MUST point to the same database with separate least-privilege roles; explicitly verify this before PILEHEAD_HISTORY_SHARED_DATABASE_READY=1. Room runtime needs SELECT(token_hash,account_id,expires_at) on account sessions; SELECT/INSERT/DELETE on consents; INSERT and SELECT(seat) on player rounds. Account runtime needs SELECT on player rounds and receipts for its authenticated query. Do not grant room runtime access to provider subjects or account preferences. Existing FK cascades need no additional application DELETE rights.
- Requires prior account/round/guest schema readiness and PILEHEAD_PRIVATE_HISTORY_SCHEMA_READY=1. PILEHEAD_PRIVATE_HISTORY_ENABLED=1 additionally requires active account and receipt features. Default off. If history recording is paused, no further personal records are made; previously recorded history remains readable with schema configured. If a DB account-deletion race rolls back terminal CAS+archive, retry via fresh authoritative state; test real concurrent deletion before activation.
- Account-linked history is subject to existing receipt 90-day expiry and expiry-only maintenance; room/member expiry cascades pending consent but not completed history. Establish maintenance and reviewed privacy notice before activation. No production migration, flag change, or paid service.
- API: authenticated room POST history-status, history-link / history-unlink (confirm:true, current round/revision, same-origin account cookie + bearer); account POST history for own records. Older clients ignore historyAvailable. The web follow-up provides consent in table Settings and a private recent-history panel within the signed-in account. Same-origin web only for consent; the cross-origin Render API remains unlinked. Browser acceptance intercepts the opt-in API and exercises the real mocked room server plus mobile and desktop profile routes. It complements, not replaces, exact SQL authorization tests and actual HTTPS/provider acceptance. Tests cover exact SQL and permissions in disposable PostgreSQL plus contract tests. Live HTTPS, cross-device privacy, concurrency and actual browser consent are release gates.
