# Public matchmaking queue foundation
**Internal-only, no public endpoint or rollout.** One proposed casual format: two human players, no ranked rating and no substitute bots. Queue ticket per verified account, five-minute lease, 20-second ready check; timing is a provisional tuning choice. A worker claims two eligible waiting tickets in a single transaction using row locks and SKIP LOCKED. Both account identities must accept their offer before it is considered ready. Duplicate tickets and outsider acceptance are rejected. Cancellation or expired offer removes both paired tickets; users may rejoin explicitly. Reciprocal blocking is checked during claim and acceptance. A blocked oldest ticket does not permanently block later compatible pairs.
 
The module does not create actual game rooms, return opponent identities, expose tickets publicly, assign ratings, or persist results. Public integration must atomically consume a ready offer into exactly one authorized room with seat credentials recovered through account-authenticated sessions, serialize cancellation and assignment, and add server-controlled deadlines, account-level abuse limits, reporting/block/mute UI, reconnect policy and bounded cleanup. No client command may invoke the worker claim operation. An authenticated waiting user is not automatically enrolled. Block writes during a ready check must be serialized with room assignment before rollout. Worker retries after lock contention are expected; no fake waiting statistics or fake opponents. 
 
Tests use exact SQL and independent PostgreSQL connections; public load, races with deletion/moderation, room assignment and real device tests remain launch gates. No production schema migration, scheduled worker or paid service.
