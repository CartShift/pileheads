# Public matchmaking queue foundation
**Internal-only, no public endpoint or rollout.** One proposed casual format: two human players, no ranked rating and no substitute bots. Queue ticket per verified account, five-minute lease, 20-second ready check; timing is a provisional tuning choice. A worker claims two eligible waiting tickets in a single transaction using row locks and SKIP LOCKED. Both account identities must accept their offer before it is considered ready. Duplicate tickets and outsider acceptance are rejected. Cancellation or expired offer removes both paired tickets; users may rejoin explicitly. Reciprocal blocking is checked during claim and acceptance. A blocked oldest ticket does not permanently block later compatible pairs.
 
The module does not create actual game rooms, return opponent identities, expose tickets publicly, assign ratings, or persist results. Public integration must atomically consume a ready offer into exactly one authorized room with seat credentials recovered through account-authenticated sessions, serialize cancellation and assignment, and add server-controlled deadlines, account-level abuse limits, reporting/block/mute UI, reconnect policy and bounded cleanup. No client command may invoke the worker claim operation. An authenticated waiting user is not automatically enrolled. Block writes during a ready check must be serialized with room assignment before rollout. Worker retries after lock contention are expected; no fake waiting statistics or fake opponents. 
 
Tests use exact SQL and independent PostgreSQL connections; public load, races with deletion/moderation, room assignment and real device tests remain launch gates. No production schema migration, scheduled worker or paid service.

## Internal assignment follow-up
Apply db/room-matchmaking-assignment.sql immediately after the queue schema. The internal assignment module atomically locks a mutually accepted offer, rechecks expiry/tickets/blocks, creates one canonical 2-human 3-round room and both seat memberships, and attaches the room to the offer. Queue leases extend to the room expiry. Assigned offers cannot be cancelled by the queue. An authenticated participant can release the assignment only after a final round, withdrawal or room expiry; the game history remains independent. Room deletion cascades the offer and both tickets. Deleting either account also cascades its offer/tickets; existing bearer sessions can still play the remaining room until expiry, so account deletion/disconnection policy must be completed before public rollout.

Seat tokens derive from a versioned independent 256-bit server-only key, offer UUID and seat; only token hashes are persisted in existing members. Recovery resolves an active account session to its own seat and verifies the stored digest before returning the bearer; no key/token logs or URLs. Retain the old key while assigned rooms exist and use a new version for new assignments. Never expose the worker claim/assignment methods as public commands. Generic public aliases avoid sharing unmoderated nicknames during this internal pilot. No public API/UI, real matchmaking worker, rate limiting, turn deadlines, seat release on disconnect, block-write serialization or production activation yet. Exact PostgreSQL tests cover rollback and authorization; actual concurrent assignment/cancellation, recovery across live devices and forced expiry need staged stress acceptance.

## Restricted Quick Play preview
The new /quick-play page and /api/matchmaking endpoint are intentionally unreachable as an active queue on canonical production. They require a separate exact HTTPS origin, shared development database, ready account and queue schemas, explicit preview flag, an allowlist of up to 50 internal account UUIDs and versioned independent server-only seat keys. VERCEL_ENV=production and pileheads.com/www.pileheads.com are hard-denied. The API checks same-origin POSTs, valid account session plus allowlist membership, an account-scoped 60/minute DB quota, and strict action shapes. No client can request a particular opponent, run a raw worker operation, or assign an arbitrary offer. A waiting/ready user's status POST drives one bounded internal claim/assignment step; no cron or background worker is added. Queue requests are idempotent on unknown outcomes by reading authoritative status, not by blind move retries.
 
Configuration: PILEHEAD_MATCHMAKING_PREVIEW_ENABLED=1, PILEHEAD_MATCHMAKING_SCHEMA_READY=1, PILEHEAD_MATCHMAKING_PREVIEW_ORIGIN (equal PILEHEAD_PLAYER_ORIGIN), PILEHEAD_MATCHMAKING_PREVIEW_ACCOUNTS (comma-separated verified internal UUIDs), PILEHEAD_MATCHMAKING_SEAT_KEYS (JSON mapping key versions to 32-byte base64url keys), PILEHEAD_MATCHMAKING_SEAT_KEY_VERSION; plus existing shared room/account DB and readiness flags. Use an isolated preview database, never copy production account data. Never print the keys. The UI only recovers a seat when the user explicitly enters the assigned table, using the existing room bearer storage and game route. No actual provider setup, Vercel environment configuration or public launch performed. Expired or terminal assigned rooms can be released explicitly by each authenticated player independently. The other player's recovery remains intact until their own release or room/account deletion; the retained offer is removed by room expiry maintenance. An expired room cannot be entered. Public launch still needs authoritative deadlines, moderation and block-write serialization, real-device and concurrency stress, privacy review, recovery/revocation policy and navigation coordination. Browser acceptance is mocked; no real external traffic.

## Independent release
Release deletes only the authenticated player's ticket, not the shared offer. This preserves the opponent's ability to recover completed results on another device. A released account can join a new queue; repeated release cannot delete a new ticket or the opponent's ticket. The existing room expiry FK cascade eventually removes the offer. Account deletion still cascades its shared offer as documented; public rollout requires the corresponding deletion/revocation policy.
