# Preview deployment access runbook
This is a non-production staging gate for guest accounts, Google OIDC, private history, progression and Quick Play. Use an isolated empty development database, never a production copy. Apply in order:
1. Room development schema and access roles; guest profile/account schemas; receipt/history/progression schemas; matchmaking queue and assignment schemas; retention access grants as appropriate.
2. Run db/preview-runtime-access.sql once as database administrator, then db/verify-preview-runtime-access.sql. All checks must be true. They verify group capabilities, not endpoint authorization, and do not replace exact SQL CI. Room and player roles are intentionally separate; neither should inherit the other or an owner role.
3. Securely provision distinct LOGINs that belong only to their corresponding NOLOGIN groups; verify no extra privileges, then configure the room and player URLs in the preview environment. Do not copy passwords or keys into source or chat. Both URLs must refer to the same isolated database, verified before setting shared-database readiness flags. Maintenance connection remains separate.
4. Configure Google test OAuth client/callback, privacy notice, exact preview origin, preview-only accounts and independent seat keys; enable feature flags in dependency order only after schema and role readiness. Review docs/PLAYER-ACCOUNTS.md, docs/PLAYER-PROGRESSION.md and docs/PUBLIC-MATCHMAKING-QUEUE.md. The Quick Play API explicitly rejects canonical production and VERCEL_ENV=production.
5. Test signed-out and authorized users, two real devices, acceptance and expiry, seat recovery, account deletion, actual HTTPS cookie behavior, live room privacy and disconnects. Verify deployment SHA and no production environment changes. No public activation or paid resource is implied by installing schemas or grants.
